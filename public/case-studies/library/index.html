Internal Component Library Based on USWDS

Overview

Project

DMX Pattern Library

Timeline

Q3 2021 - Q2 2022

Team

UX Designer, UX Architect, Content Strategist, Developer

Role

UX Architect

Built and maintained an internal component library and page templates based on the United States Web Design System (USWDS). The library was used to standardize UI across multiple public sector website redesign projects, improve accessibility compliance, and enable faster, scalable page creation.

Tech Stack

  • HTML
  • CSS
  • Markdown
  • Web Components
  • Jekyll
  • Eleventy
  • Netlify
  • GitHub

Problem

Across multiple government projects, teams were rebuilding the same UI components from scratch. This slowed development, created inconsistent user experiences, and led to accessibility issues that were often caught late.

Context and Constraints

This system supported multiple government websites, each with different branding and strict compliance requirements.

Key constraints:

Accessibility was required

All components needed to meet Section 508 and WCAG standards

Brand flexibility

Each agency had its own typography, colors, and visual identity

Multiple audiences

Designers, developers, and content strategists all needed to use the system

Technical limitations

The system was built with static HTML, CSS, and JavaScript, which limited built-in interactivity

My Role

My main focus was turning design guidelines into reusable, production-ready components that teams could actually use.

I worked closely between design and development to determine how the system would be implemented and how it would evolve over time.

Owned Outright
  • Building the component library and page templates
  • Ensuring accessibility was built into every component
Shared Ownership
  • Defining how components should be structured and reused
  • Creating a system that could adapt to different brand styles
  • Establishing workflows for contributing and maintaining the library

Solution

Our team built a shared pattern library based on the United States Web Design System (USWDS). The goal was to give teams a reliable set of reusable components and templates so they could move faster while maintaining consistency and accessibility.


Within the first year, the library was adopted across 5+ projects. Teams reduced design-to-development back-and-forth, reused components instead of rebuilding them, and shipped more consistent, accessible interfaces.

Engineering Challenges & Solutions

Designing for Multiple Roles

Challenge: The system needed to work for designers, developers, and content strategists.

Decision: We structured the system so each group could work in a way that matched their needs:

  • Developers used component code directly
  • Designers worked from predefined patterns and templates
  • Content strategists managed content through Contentful

Tradeoff: This required more upfront structure and documentation.

Outcome: Teams could work more independently, reducing handoff friction.

Flexibility vs. Consistency

Challenge: Support different brand styles without fragmenting the system.

Decision: Allow customization through design tokens instead of unrestricted styling.

Tradeoff: Fully custom designs were limited.

Outcome: Projects stayed visually consistent while still meeting most branding needs.

Reuse vs. Customization

Challenge: Make the system reusable without blocking project-specific needs.

Decision: Maintain a central core library and allow teams to create project-level versions.

Tradeoff: Updates to the core system required coordination across projects.

Outcome: Teams could customize their implementations without duplicating the entire system.

Static vs. Dynamic Architecture

Challenge: Static site generation limited interactivity.

Decision: Static templates were used for structure while Contentful provided dynamic content.

Tradeoff: Complex interactions required additional engineering work.

Outcome: The system remained fast and maintainable while supporting dynamic content where needed.

Accessibility as a System Feature

Challenge: Accessibility requirements needed to be consistently met across multiple teams and agency websites.

Decision: Accessibility was built directly into the component library through semantic HTML, keyboard navigation, focus management, and approved design tokens.

Tradeoff: Restricting customization reduced flexibility but ensured accessibility standards were maintained.

Outcome: Accessibility became a built-in feature rather than something teams had to implement independently.

Impact

Reduced Duplication

Minimized repeated front-end effort across multiple teams.

Consistency

Standardized component behavior and layout patterns.

Built-in Accessibility

Embedded compliance directly into production components.

Faster Onboarding

Enabled teams to ship new pages quickly using reusable templates.

Scalable Foundation

Created a system that can grow alongside new products and services.

Key Engineering Challenges & Solutions

Component Architecture

  • Designed a modular, reusable component structure for consistency and scalability
  • Built components with configurable variants and accessible defaults
  • Documented usage patterns for developers to easily consume and extend

Template System

  • Created reusable page layouts using static site generation
  • Enabled teams to quickly create new pages without duplicating code
  • Structured templates to support future CMS integration

Accessibility

  • Used semantic HTML and ARIA attributes across components
  • Implemented keyboard interactions and focus management
  • Reduced accessibility risk across all public sector redesign projects

Build & Deployment Optimization

  • Migrated from Jekyll to Eleventy for faster, more flexible builds
  • Automated deployment to Netlify
  • Managed contributions and updates through GitHub workflows
